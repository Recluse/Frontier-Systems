# Windows engine performance baseline

Measured October 9, 2026 local time (October 10 UTC), against the working tree based on commit `f830bcb`, including the uncommitted consciousness foundation/owner. Godot 4.7.2 official debug executable; Windows 11 Pro; i9-13900KF, 24 cores/32 logical processors; approximately 64 GiB installed RAM; RTX 3080 Ti, NVIDIA driver 32.0.16.1714. Full environment: [hardware.json](hardware.json).

## Findings

The current small engineering runtime has substantial idle tick headroom. The simple desktop scene is inexpensive to render on this hardware. These results do **not** establish multiplayer population capacity or VR readiness.

The main CPU scaling concern is full receipt-history copying/validation in domain commits: 64 consciousness owners assessed together take about **56.36 ms**, exceeding the **16.67 ms** 60 Hz tick budget. The same 64 pure plans take about **2.11 ms**; those use uncommitted alert inputs and therefore are a component comparison, not identical end-to-end state transitions. A saturated linear-motion owner costs about **2.28 ms per paired impulse commit**.

No runtime optimization was applied during this task. Benchmark setup was corrected before final measurement: repeated inner-door closure against the default vacuum pressure differential failed the actuator-force check. Final command runs use valid repeated vent-close commands and have zero rejections/drops. The saved runtime report is the corrected successful run, not the discarded first pass.

## CPU results

Five repeats per scenario. Means below average the five equally sized repeat means; p95 is the **highest per-repeat p95**, not a pooled percentile. Times include debug-build overhead and other activity on the user's PC.

| Workload | Mean | Highest repeat p95 | Scope |
| --- | ---: | ---: | --- |
| Idle world tick, history off | 0.017 ms | 0.019 ms | 2,000 measured ticks/repeat |
| Idle world tick, history on | 0.045 ms | 0.061 ms | Includes bounded history capture |
| 64 valid commands/tick | 1.863 ms | 2.136 ms | 200 measured ticks/repeat; history on |
| 256 valid commands/tick | 7.307 ms | 7.927 ms | Current maximum commands/tick; history on |
| Validated world snapshot + JSON | 1.428 ms | 2.636 ms | 200 captures/repeat; 6,464 bytes |
| 64 consciousness pure plans | 2.113 ms/batch | 2.800 ms/batch | 50 measured batches/repeat |
| 64 consciousness owner commits | 56.364 ms/batch | 60.838 ms/batch | Full 64-receipt history per owner |
| Paired linear-motion commit | 2.276 ms/commit | 2.549 ms/commit | Full 128-receipt history |

Runtime/command measurements warm up for 100 ticks; snapshots for 20 captures; consciousness for 70 batches; motion for 140 commits. All CPU scenarios run sequentially, manually advancing isolated fixed ticks faster than real time. They are service-time measurements rather than achieved engine FPS or real-time pacing tests. Raw repetitions, runner diagnostics and per-system reports: [runtime.json](runtime.json).

Command creation/enqueue is measured separately: about **0.496 ms** for 64 commands and **1.988 ms** for 256 commands. Those costs are excluded from the tick column. Mean whole setup-plus-tick work is consequently about 2.36/9.29 ms respectively. A server producer's actual workload can differ substantially from this synthetic local allocation path.

At 256 commands/tick, **one of 1,000 measured ticks exceeded 16.67 ms**, with a maximum 19.662 ms. At 64 commands/tick and both idle settings, no measured tick exceeded the budget. History capture adds approximately 0.028 ms to the idle mean. Built-in tick timing excludes history observer costs; the benchmark's outer stopwatch includes them.

The default world contains four registered systems: pressure (three volumes, three sensors, one airlock), access control (one device), machine control (two installed modules, one wire), and inventory (two logical bodies). The idle benchmark has no active grip sessions, inventory jobs, search views or gas transfer. It does not stress populated inventories, active wiring networks, bulk atmospherics or physics crowds.

## Actual desktop rendering

Each rendering profile runs the real main client for five seconds warmup plus fifteen measured seconds. VSync is requested off and `Engine.max_fps` set to zero. Requested window resolution: 1280x720. Actual root viewport: **1152x648**; habitat subviewport: **523x504**. These are small illustrative viewports, not 1080p gameplay or headset eye buffers.

| Profile | Observed FPS from mean frame interval | Frame interval p95 | Mean render CPU | Mean render GPU | Engine static / reported video memory |
| --- | ---: | ---: | ---: | ---: | ---: |
| Forward+ / D3D12 | 75.0 | 13.509 ms | 0.156 ms | 0.079 ms | 106.4 / 117.4 MiB |
| Mobile / Vulkan | 120.0 | 8.498 ms | 0.132 ms | 0.050 ms | 94.9 / 55.4 MiB |

Forward+ reported 397 nodes, 2,616 objects, 64 draw calls and 6,948 primitives at the final sample. Reported memory is engine static allocation/video allocation, not total process working set or proof of leak absence. GPU driver and platform allocations are not fully captured.

Frame intervals stayed close to 75/120 Hz despite requested uncapped settings. Rendering timestamps are much smaller than those intervals, suggesting another pacing limit; its exact cause was not established. **Do not interpret the FPS difference as a demonstrated maximum-renderer-throughput advantage.** Both renderer and graphics driver change between profiles, and there is only one measured session per profile.

Render CPU sums viewport measurements and shared setup; GPU sums viewport measurements. These exclude script/other engine CPU work and are not interchangeable with end-to-end frame latency. Measurements themselves add overhead. Godot documents the [viewport render timing semantics](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu). Physics monitor samples are periodic gauges, not a unique measurement for each physics tick.

Raw rendering results: [Forward+](client-forward_plus.json), [Mobile](client-mobile.json). No headset or OpenXR session was activated. Mobile is a desktop baseline for the optional VR rendering profile; stereo, tracking, encoding/link transport and Quest latency remain unmeasured.

## Recommended next work

1. **Optimize domain commit hot paths before health/motion runtime integration.** Keep exhaustive saved-record validation on loading/untrusted boundaries. Validate current state plus the proposed change during normal commits, using encapsulated bounded receipt append/eviction rather than re-decoding/copying the entire history. Preserve detached public observations, atomic failure and idempotency tests.
2. **Stagger physiology assessments.** The current 64-owner batch averages 56.36 ms. A naive synchronized 10 Hz assessment would cause large tick spikes; distribute work across ticks with bounded queues and priority for urgent injury changes. Scheduling alone does not remove the total cost.
3. **Set a command-work budget in addition to count.** Current 256-command bursts show rare overruns. Measure richer inventory/control commands before adopting a production count and deferred-work policy.
4. **Benchmark realistic entity workloads.** Add active inventory/grip work, dynamic collisions, angular motion, atmosphere transfers, moving assemblies, persistence/network traffic and larger generated content as implemented. Rerun after owner optimizations to confirm the expected reduction.
5. **Measure actual play targets.** Full-resolution first/third-person scenes, crowded physics interactions, lower-end PCs and Quest 3 PCVR at its intended eye resolution/refresh rate need separate runs. Profile frame pacing/present waits rather than increasing scene complexity to guess the cap.

## Reproduction

The harness now supports [60/72/90 Hz candidates](../../docs/development/simulation-rate-benchmark-matrix.md) and writes rate-qualified filenames. The raw files linked above are the original 60 Hz measurements; candidate runs are pending.

From the project directory, run these sequentially. The rendering commands open the prototype window and close it automatically. Each overwrites its matching raw report; archive prior reports first if comparing revisions. Scripts use isolated synthetic state and do not write saves, change preference files or call external services.

```powershell
$godotBench = 'D:\Godot_v4.7.2-stable_win64.exe\Godot_v4.7.2-stable_win64_console.exe'
& $godotBench --headless --xr-mode off --path . --script res://tools/godot/benchmark_runtime.gd
& $godotBench --xr-mode off --path . --resolution 1280x720 --script res://tools/godot/benchmark_client.gd
& $godotBench --xr-mode off --rendering-method mobile --rendering-driver vulkan --path . --resolution 1280x720 --script res://tools/godot/benchmark_client.gd
```

These opt-in performance measurements are not fixed-threshold CI tests. CI correctness checks remain separate; hosted runners would not provide comparable GPU/timing results.
