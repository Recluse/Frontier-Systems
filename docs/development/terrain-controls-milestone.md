## Transport, projection and retries

Trusted two-slot `FirstPlayableHost` policy grants `terrain.operate` alongside inventory access after invite authentication. Terrain frames add exactly `request_number` to the existing command envelope and require `request_id = terrain-client-<ordinal>`. Clients supply only the original intent, stable cell ID, amount and observed revisions. Context, principal, tool choice, target position, owner sequence and authoritative records come from the host/domain. Unknown extra fields fail closed.

The domain ID deliberately repeats between peers. Pending host routes use authenticated principal **and connection session** plus domain ID, bounded to 32 entries. Disconnect drops peer routes, targeted outbound events and a targeted checkpoint reply; an already authorized queued command may still commit. A later session reconciles its original request through durable domain receipts. A null-context completion from unrelated world work cannot enter host routing.

`terrain-observation-v1.schema.json` defines the read-only projection: two stable dirt cells, positions in millimetres, mass/capacity in milligrams, revisions, advisory work readiness/message, own escrow and next fresh ordinal. It excludes foreign claims, receipts and authentication data. The bounded decoder verifies shape, stable IDs/positions, integer numbers, finite capacities, provenance parcels and visible mass before publishing detached data. Malformed views close the client and disconnect clears projections. The observation work gate reuses canonical inventory reach/consciousness, actual active component-backed shovel and free supporting-hand checks. It neither authorizes a later command nor imports mass.

`RemoteWorldRuntime` freezes one unresolved terrain intent before sending. It rejects changed intent or fresh work while uncertainty remains; `next_request_number` is used only for fresh requests. A bounded local journal follows `terrain-client-intent-v1.schema.json` (8 KiB), storing world/region/invite slot and original ordinal/payload, with no keys or owner state. Bootstrap enables it in `user://terrain-client-intents`. Write failure prevents a send; clear failure leaves exact reconciliation available. Restart loads the matching journal and the panel offers an explicit original-intent retry. Repeated `request_pending` preserves uncertainty. Explicit rejection releases the ordinal for corrected fresh work. The journal is untrusted client data; the host still authorizes and validates every request.

Terminal acknowledgement invalidates the client's fresh-work terrain view until a post-completion host projection arrives. This prevents an immediate second button press from reusing the pre-ack next ordinal as fresh work. The original journal remains the only retry source during uncertainty.

Real wire tests found that JSON numeric payloads were retained as floats while domain receipt decoding normalized them to integers. The runtime now normalizes validated intent integers **before** retaining an allocation, making wire commits, checkpoint receipt comparison and restart retry agree. This does not refresh revisions or change intent values.

The panel shows selected source/fill cell position, remaining mass/capacity/revision, own escrow, held tool, inventory/tool revisions, host capability and rejection feedback. It disables fresh actions during uncertainty but allows original reconciliation independently of current work capability. Two visual markers show the stable cells; they have no collision and do not edit terrain geometry. Bootstrap additions affect client setup only and preserve independent host-startup recovery wiring.
