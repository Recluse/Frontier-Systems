# Player movement feedback milestone

The actual first-playable shell previously wrote a movement rejection into the general connection label, then replaced it on the next host observation. A player whose local capsule snapped back could lose the explanation in the same socket poll. Movement correlation also retained a string ID after completion. Correction left the last submitted pose as the sampler baseline, causing the corrected stationary view to submit another movement.

A wrapped label beside the view now distinguishes an observed host position, a submitted movement awaiting acceptance, exact acceptance of that submitted movement, a rejected movement and visual correction, a failed enqueue, and the end of a session. It keeps one bounded result with at most 512 characters of adapter reason. Observations preserve pending/completed feedback within the session. A fresh session observation resets it. No history, persistence, retry button or receipt replay is added.

Only the exact in-flight InventoryDevelopmentCommand object can settle movement. Completion/disconnect clears that reference. A transport-disconnected completion reports an unknown outcome rather than a host rejection. Existing rejection reconciliation returns the local capsule to the latest host observation and now synchronizes the sampler baseline, so correction alone does not submit a phantom command. Ordinary new local motion still uses the existing 0.15-second sampler and one-in-flight transport.
