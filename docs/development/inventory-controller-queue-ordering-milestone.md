# Inventory controller queue ordering prerequisite

## Owner and cadence

`InventoryRuntimeCommandQueue` is explicitly composed by a trusted same-process simulation owner over one actual `InventorySimulationSystem`. Initialization creates its own `InventoryRuntimeCommandGate`; the owner obtains the gate authority through `controller_authority()` and performs synchronous trusted bind/replace/revoke transitions before calling `advance_tick(tick, fixed_delta)`. The queue drains through the gate, then calls inventory `simulate_tick` once, so commands precede job advancement. Do not separately register or advance that inventory in a runner. The component is not installed in WorldRuntime or any network/admission path. Composition is one-shot after success.

The existing SimulationRunner uses bounded FIFO command dispatch before system ticks; this prerequisite follows that pattern without adding command envelopes, transport callbacks, a second receipt protocol or a generic queue framework. Its single boundary call couples draining and inventory advancement, allowing port-free lifecycle ordering tests without changing production orchestration.

## Bounds and deterministic failure

Admission receives trusted pinned opaque token identity, a server-authenticated context and detached plain intent. It copies scope/principal/session and boolean permissions; inventory does not use tool grants. Context identities use existing stable-ID validation; at most 32 permission entries are retained. Intent permits only null, bool, integer, string, array and string-keyed dictionary values, with depth at most four, 128 value nodes and 256 characters per string/key. Objects, resources, floats, cyclic/excessively nested values and unknown operations fail admission. Existing canonical validators still own exact intent fields, grants, capability and revision checks.

Capacity is 1..64, default 64; per-tick attempts are 1..capacity, default 16. FIFO order is successful enqueue order, recorded by a monotonically increasing exact-integer sequence. Full queues refuse the newest command and retain existing order. Sequence exhaustion refuses future admission without wrapping; accepted entries still drain. Both successful and failed gate dispatches consume the per-tick budget. Leftovers retain order for the next tick. Returned outcome arrays contain at most the configured per-tick count and are never retained by the queue. Admission success is only a volatile queue sequence, never a canonical receipt. Duplicate request IDs are passed to existing canonical receipt semantics; the queue adds no replay or retry policy.

Only the consecutive next tick is accepted. Duplicate/skipped ticks and invalid delta fail without draining or advancing inventory; the caller must supply the missing consecutive tick. External advancement of the inventory fails closed rather than resynchronizing and replaying commands. The owner must not share this advancement responsibility. Reentrant enqueue/drain/disconnect calls during dispatch fail. Gate validation runs for every application; stale/replaced/revoked contexts and denied provider sessions produce transient failures without canonical command mutation. A failed command does not prevent later FIFO attempts.

## Persistence, restore and disconnect

The queue, copied contexts and tokens are volatile. No snapshot/schema or operation receipt contract changes. Every enqueue, drain and disconnect cleanup checks the canonical inventory restore generation. A changed generation clears pending intent, retains the non-wrapping sequence, and resynchronizes the tick from the restored snapshot. The first enqueue/drain that detects restore returns `queue_restored`; it never applies old commands. Restore during provider validation interrupts the drain, discards the remainder and skips job advancement. Already applied commands before a restore have no queue replay: the trusted restore determines canonical state. The caller must explicitly reconcile controller authority and bind/pin fresh credentials before new work succeeds.

Trusted disconnect handling calls authority revoke and `discard_session(principal, session)`; the latter removes only matching pending entries and has no canonical effects. If cleanup is omitted, provider denial still rejects the old command at application. Detached context grants are trusted admission-time values; changes to authentication/grants must be reflected by provider denial or a controller lifecycle transition, not by editing the original context. The queue does not infer authentication revocation from mutable caller objects.

Profiling exposes bounded pending/peak and saturating attempts/rejections/discarded/sequence values. Outcomes are transient; no callbacks, waits, external services, ports or unbounded history are introduced. Full snapshots are inspected at the boundary to verify sole tick ownership; this is bounded by existing inventory contracts and is a prerequisite correctness check, not a measured production performance claim.

## Acceptance and limits

`inventory_runtime_command_queue_test.gd` uses actual inventory, health, controller authority and gate. It covers detached input, FIFO partial drain, full refusal, duplicate/skipped boundary conservation, canonical receipt retry, queued replace/revoke/provider denial, bounded plain intent, unknown operations, real search-job timing, identical-epoch restore cleanup, unreconciled stale denial, fresh success, scoped disconnect cleanup, provider-callback restore/reentrancy, sequence exhaustion and external advancement/freed runtime refusal. Existing gate, authority, lifecycle, self/world/grip/runtime and checkpoint tests remain regression gates. The versioned port-free `tools/ci/run-godot-checks.ps1` runner uses pinned Godot 4.7.2; `.github/workflows/ci.yml` discovers tests on Windows and Ubuntu.

This establishes a same-process prerequisite, not production network admission, client/controller usability, graphical/VR acceptance, live-service behavior or deployed performance. No movement, presentation, shared schemas, receipt contracts, dependencies, configuration or art change. First-party code and documentation are MIT. No merge, release or deployment is performed.
