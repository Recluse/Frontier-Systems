# Terrain portable material milestone

## Owner, cadence and physical record

`TerrainSimulationSystem` adds one server-bound `TerrainMaterializeCommand` executed synchronously at the next authoritative fixed tick. Its `materialize` entry point consumes permission to use one **whole own escrow transfer** and creates one `item.terrain-parcel.prototype` revision 1 in the claimant's existing inventory body root. Clients cannot supply item IDs, amounts, material records, origin parcels or a destination. There is no wire endpoint or UI in this slice.

`TerrainMaterialOwner` remains the sole canonical matter owner. Its existing immutable-for-portable transfer contains exact integer milligrams, pinned material ID/revision and origin-ID parcels. A new association connects that record to deterministic `terrain-item-<excavation sequence>` physical identity; it carries no second mass/provenance copy. Inventory continues to own physical parentage and equipment. Each live transfer is exclusively usable escrow or a portable payload. Materialized records are hidden from the existing escrow observation, cannot be filled and cannot be materialized again. Domain owner/intent/receipt schema v1 is unchanged.

The parcel has zero intrinsic shell mass, no storage and a conservative fixed 1,000 mL inventory volume. The dirt fixture permits at most 1,000,000 mg per excavation; its prototype density is 1,200 kg/m3, so this volume ceiling covers the largest whole transfer. Small transfers retain the same conservative reservation. This is neither a container shell nor a density/packing/geometry simulation. Existing equip, stow, drop, pickup and shared transfer policies operate on the physical item and include its payload mass. Moving it to another body does not change material provenance or the original claim receipt.

Production's independent 25 kg fixture is untouched. Parcels have `terrain.parcel`, not `resource.carrier`, and are excluded from Production inputs/recycling. There is no portable-to-terrain fill, production consumption, deletion or portable payload mutation in this milestone. A later explicit transaction contract must release this immutable association before any consumer can debit the canonical terrain matter.

## Authority, atomicity and retries

The existing world/region-bound `terrain.operate` grant and registered inventory principal authorization apply before retries. New claims additionally require voluntary consciousness, an available unreserved inventory hand and the exact current inventory revision. Because the escrow is already assigned to a principal, materialization uses that principal's body root and needs no new terrain reach or shovel check. It neither excavates additional matter nor changes a cell revision. Source operations retain their existing reach, actual component-backed shovel and supporting-hand gates.

The exact payload is `transfer_id` and `expected_inventory_revision`. The independent principal claim ordinal starts at 1; command ID is `terrain-materialize-<ordinal>`. Ordinals cannot skip or change retained intent. Claim attempts share the existing limit of 16 terrain ingress attempts per fixed tick. They create no autonomous tick work, wear, I/O, async callback or service dependency.

The bridge prepares the physical item through the existing inventory equipment factory boundary using prospective **complete** payload masses. All item, body, root, equipment, volume, count and revision checks occur before adoption. For synchronous adoption only, it installs the prospective portable association and its derived mass projection. Inventory adoption failure restores both before returning; no successful ordinal or escrow permission is consumed. Successful adoption settles physical ownership, association and permission together without an await or later fallible mutation. Distinct competing claims with an earlier inventory revision reject; an exact duplicate returns the same detached receipt.

The portable association retains the original claimant, ordinal, transfer/item IDs and expected inventory revision. The receipt resolves the same canonical transfer material/provenance. Exact retries are authenticated read-only reconciliation: no current revision, consciousness, hand, location or item ownership recheck repeats the physical action. This remains true if the parcel moves to another body and after restart. Changed intent, a new ordinal for an already materialized transfer or a foreign claimant rejects.

There are at most **128 lifetime portable associations**. They are never evicted, including after the domain owner's 64 excavation/fill receipts expire. This intentionally bounded slice has no garbage collection/recycling; saturation rejects new materializations while retained retries remain valid. Principal claim ordinals are therefore bounded to 128. Cells, origins, owner transfers and domain receipts keep their earlier limits. `portable_items` augments existing observational commit/retry/rejection profiling counters. The mass projection is a bounded derived cache, regenerated from the owner and associations on restore, never serialized or used as a second matter owner.

## Payload composition and checkpoint version

Inventory retains **one catalog mass provider**. `InventorySimulationSystem` composes the existing Production per-item provider with one disjoint Terrain payload projection. Production prospective factory/graph checks automatically include current terrain mass; terrain preparation includes current production mass. Overlapping nonzero mass ownership rejects. This introduces trusted synchronous API additions (`bind_external_payload_masses`, prospective external masses and a whole-checkpoint mass view), without changing inventory snapshot v4 or ledger item records.

Terrain checkpoint **v2** adds the bounded `portable` association map to the existing v1 bridge envelope. V1 restores with an empty map; absent legacy terrain still commissions zero matter. A v1 snapshot carrying physical terrain parcels without associations rejects. Recovery never regenerates excavated material. World envelope v1 accepts either explicitly versioned terrain record, matching the existing additive system version policy.

Recovery validates both canonical payload owners before composing candidate masses. A synchronous scoped inventory view supplies those **candidate** payloads throughout all cross-system validation and ordered restore, including Production's intermediate load refresh. It is cleared before returning, and successful recovery refreshes loads from the restored owners. A candidate is never checked against the old world's payloads. Rejection leaves canonical world state unchanged.

Validation checks owner conservation and replay, exclusive escrow/portable coverage of all transfers, deterministic physical IDs, unique complete per-principal claim ordinals, unique and increasing inventory commit revisions, matching retained physical factory receipts, known claimants, physical item/association bijection and committed revision bounds. Claim rewind includes original portable claimants, so the existing retained excavation/fill tail still verifies. A physical item may belong to another body after a valid transfer. Checkpoints must be atomic and trusted; these consistency checks do not authenticate rewritten storage or reconstruct an unbounded creation history.

Construction coverage metadata/schema **v2** adds the actual `terrain.materialize` special factory alongside existing plate and tool-part factories. V1 metadata/schema are retained. This explicit catalog contract change adds no Production runtime consumer or blueprint; `construction_catalog_test.gd` checks the new creation path.

Schemas: `terrain-system-v2`, `terrain-materialize-command-v1`, `terrain-portable-receipt-v1`, and the additive terrain union in `world-snapshot-v1`. Runtime relationship checks remain authoritative beyond schema shape validation. JSON recovery preserves every numeric value and provenance parcel; legacy integral float representations normalize through existing inventory decoders, and the normalized full checkpoint is byte-stable on another restart.
