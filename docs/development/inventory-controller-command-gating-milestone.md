# Inventory runtime controller command gate

## Contract and composition

`InventoryRuntimeCommandGate` is an explicitly composed, same-process command application boundary. Trusted server composition calls `initialize(inventory, world, region, provider)` with its canonical runtime, server-owned scope IDs and session provider. The gate constructs its own `InventoryControllerAuthority` with an `InventoryRuntimeControllerOwner` over that exact runtime; an authority from another owner cannot be injected. Initialization is one-shot after success. `controller_authority()` exposes trusted synchronous bind/replace/revoke/pin/reconciliation operations to the composing owner, never to transport clients.

The caller supplies an opaque pinned token and server-created `AuthenticatedCommandContext` to `apply` at the next fixed tick boundary. The gate resolves the actor through canonical principal/body ownership, validates the current token/context against that body and composed world/region, then synchronously invokes existing canonical `apply_local` operations. Principal, body and scope are never taken from intent. Existing exact intent fields, capabilities, revisions, receipt idempotency, conservation, job limits, search scopes and grip arbitration remain authoritative. A token pinned before queueing must still pass application-time validation.

The allowed operations are self, world, start, cancel, resume, resist, close_search, grip_join, grip_release and grip_resume. Fixture movement is excluded. No gate method implicitly binds, pins, reconciles or falls back to development authorization. Missing, foreign, replaced, revoked and restored tokens fail, as do wrong scope, session, principal, grants, provider denial and development-local contexts. Unreconciled restore blocks application; reconciliation retires old identities, and a fresh bind/pin is required even for the same session and identical saved epoch.

## Ownership, cadence, persistence and failure

The composing server owner retains the gate, authority and provider. Application occurs synchronously before the inventory system's tick priority 200 progress/completion. There are no external effects, network calls, waits, process orchestration or ports. Gate and token identities are volatile; inventory snapshot v4 and schemas remain unchanged. The existing restore generation and lifecycle invalidation contracts continue to own fencing and cancellation of jobs/views/grips.

A failed gate admission never invokes canonical command operations and preserves inventory snapshots, jobs, grips, items, receipts, search views and outcome metadata. Existing canonical operation failures retain their existing error contracts. Gate profiling exposes saturating counters for applications (canonical command dispatch attempts, including canonical rejection), observations (scoped read dispatch attempts) and rejections (pre-dispatch refusal), bounded by the authority's exact-integer maximum. Authority counters remain separate. This adds no unbounded retention. The same gate now also supplies the [controller-gated scoped read surface](inventory-controller-observation-gating-milestone.md).

## Acceptance and limitations

The port-free `inventory_runtime_command_gate_test.gd` composes actual inventory and health runtimes with the runtime controller owner. It exercises bind, valid self receipt and retry, completed search, grip and pending job, replacement/revoke, identical-epoch restore, explicit reconciliation, fresh same-session success, denial matrices across every allowed operation, exact snapshot/counter and volatile observation conservation, client identity-field rejection, fixed-tick refusal, one-shot composition, provider-callback restore and freed-owner failure. Existing authority/lifecycle tests independently exercise restore fencing and scoped invalidation.

Run the versioned `tools/ci/run-godot-checks.ps1` with pinned Godot 4.7.2 and the new test plus inventory authority, lifecycle, runtime, self/world/grip and checkpoint regression tests. `.github/workflows/ci.yml` discovers the test on Windows and Ubuntu. Report actual results and exact PR head separately from pending CI.

This is a prerequisite component with no production admission, network/session rollout, receipt high-water policy, startup rotation, UI or observer rollout. Existing `InventoryDevelopmentCommand` and direct `apply_local` remain an explicitly separate fixture/internal surface, not a controller-gated transport endpoint. The gate is not installed into `WorldRuntime`; future admission must explicitly route authenticated inventory commands through it and keep fixture routes inaccessible. No shared schemas, presentation, locomotion, transfer preview, configuration, dependencies, artwork or license provenance changed. Headless checks establish no graphical, VR, live-service or deployed acceptance. First-party changes are MIT; no merge or release is performed.
