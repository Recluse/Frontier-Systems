# Discord Social SDK and DiscordPHP

Research note for the Godot colony simulation plan. Checked against official Discord and current DiscordPHP documentation on 2026-10-09. The user maintains DiscordPHP and says it now supports the Social SDK; this review treats that as context and confirms relevant support in its current public docs.

## Which Discord features fit the game, and what are the limits?

### Takeaway

The Social SDK can power an in-game social layer: Discord account linking, friend/relationship views, Rich Presence, invites and join requests, DMs, text chat in game-managed lobbies, lobby voice, and optional linked Discord text channels. This is a strong fit for social coordination around a persistent colony game. Discord's lobbies are communication groups, however, not a durable world/session database. Their size, idle lifetime, chat-history window, development rate limits, and full-release access review all need to be treated as product constraints.

### Cited Findings

- Discord describes its Social SDK as a distributed C++ library that ships inside the game. It exposes data and operations, not the game's UI. Documented features include account linking, friend relationships, Rich Presence, activity invites, DMs, lobby chat/voice, and linking a Discord server text channel to an in-game lobby. [Discord Social SDK overview](https://discord.com/developers/docs/social-sdk/index.html)
- Presence/friends/invites use the `openid sdk.social_layer_presence` scopes. DMs, lobby chat/voice, and linked channels use `openid sdk.social_layer`; Discord describes these communication features as limited access. [OAuth2 scopes](https://docs.discord.com/developers/discord-social-sdk/core-concepts/oauth2-scopes)
- Communication features are available for development and testing with application-wide limits. Current published limits include 100 lobby create/join or update operations per two hours, 20 channel-link changes per two hours, and 100 lobby-message or DM sends per two hours. Production-scale use requires applying for increased limits. The review requirements include account linking, Rich Presence, game invites/Discord joins, a unified friends list with full Discord-friend access, complete user flows and failure states, age safeguards, and supporting material. Discord may approve or deny the request. [Communication features and production access](https://docs.discord.com/developers/discord-social-sdk/core-concepts/communication-features)
- Lobbies support text and voice and can be administered either with Discord's HTTP API or client-side through `Client::CreateOrJoinLobby`. Voice is recommended for around 25 or fewer participants, even though the lobby itself can hold up to 1,000. Server-created lobbies support an idle timeout up to seven days. Client-created lobby secrets expire after 30 days; their lobby defaults to five minutes of idle time. SDK disconnect does not remove membership by itself. [Creating and managing lobbies](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-lobbies), [Discord Lobby API](https://docs.discord.com/developers/resources/lobby)
- Lobby chat history fetch is limited to 200 messages and at most 72 hours, and the player must still belong to that lobby. The Discord client SDK keeps a small recent-message cache, not a game archive. [Lobby chat history](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-lobbies), [MessageHandle reference](https://discord.com/developers/docs/social-sdk/classdiscordpp_1_1MessageHandle.html)
- Discord's published docs conflict on per-user lobby count: the overview/reference says 200 lobbies per game, while the current lobby-management guide says 100. Treat 100 as the conservative planning cap and confirm with Discord before designing around a higher number. Both sources agree on the 1,000-member lobby ceiling and ~25-person voice recommendation. [Social SDK LobbyHandle reference](https://discord.com/developers/docs/social-sdk/classdiscordpp_1_1LobbyHandle.html), [Creating and managing lobbies](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-lobbies)
- Rich Presence party data can carry an accepted-join secret; the game can use it to join the corresponding lobby or resolve a game-server join ticket. Activity invites and join requests are surfaced through SDK callbacks. [Activity reference and invite flow](https://discord.com/developers/docs/social-sdk/classdiscordpp_1_1Activity.html)
- The SDK's voice call API is tied to a lobby. It exposes call/participant status, speaking state, self mute/deafen, local mute/volume, voice activity detection and push-to-talk. `StartCallWithAudioCallbacks` exposes per-user captured/received audio buffers for custom processing. Discord's official proximity-voice example uses those streams with the engine's audio system to apply 3D positioning; the game must implement the positional/radio effect itself. [Managing voice chat](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-voice-chat), [Discord July 2026 developer newsletter](https://discord.com/developer-newsletter/july-2026)
- Social SDK has a provisional-account path: players can use friends, DMs, lobby chat and voice without a linked Discord account. Provisional accounts depend on the game's external identity provider and can later merge into a Discord account. [Provisional accounts](https://docs.discord.com/developers/discord-social-sdk/development-guides/provisional-accounts/overview)
- Linking a Discord channel forwards messages between the linked channel and lobby. Discord warns that a user can link a private server channel; all lobby members can then see and reply to those messages. The UI must explain this exposure, or should limit linking to channels that are visible to all lobby members. [LobbyHandle linked-channel guidance](https://discord.com/developers/docs/social-sdk/classdiscordpp_1_1LobbyHandle.html), [Linked Channels guide](https://docs.discord.com/developers/discord-social-sdk/development-guides/linked-channels)
- Discord says linked Discord friend information should not be copied and stored by the game; unlinking must remove those entries from the in-game list. Its terms also require personal API data from users without a linked account to be processed only as necessary for the feature and deleted on request or when the integration ends. [Communication feature approval requirements](https://docs.discord.com/developers/discord-social-sdk/core-concepts/communication-features), [Social SDK Terms](https://support-dev.discord.com/hc/en-us/articles/30225844245271-Discord-Social-SDK-Terms)

### Inferences

- Treat a Discord lobby as an optional communications cohort (crew, base team, expedition party, or radio group) mapped to an authoritative game-world group ID. Do not make Discord lobby existence, membership, chat history, or availability authoritative for colony ownership, access control, simulation state, or persistence.
- Use a server-managed lobby for groups needing game-controlled membership and reconnection policy; use client-created secret lobbies for short-lived, friend-joinable groups. Reconcile/recreate expired communication lobbies from game-server state. Keep active voice cohorts well below 25 participants, and avoid creating one lobby per room, device, player, or small state change because of caps and current development rate limits.
- Proximity/radio audio is feasible as a later native-audio milestone, but it is not a checkbox feature of the Social SDK. Prototype it independently: the extension would route per-user callback audio into Godot's audio pipeline and apply attenuation/filtering from authoritative simulation state. Preserve ordinary group voice as the simpler first version.
- Plan for a Discord communication-access application before committing production chat/voice to the launch critical path. The published minimum access criteria imply a real social product surface—especially friends, presence, linking, invites, denial/error handling—not just voice transport.

### Gaps

- Per-user lobby count differs between Discord's current pages (100 vs. 200); confirm with Discord before any design assumes the larger limit.
- Increased production limits/access are reviewed by Discord and are not guaranteed by the public documentation. The schedule and final quotas cannot be known from these docs.
- Verify the intended target platforms and current Social SDK release during implementation. Discord currently lists Windows/macOS/Android/iOS support as generally available and Linux as experimental; console use requires platform middleware approval. [Platform compatibility](https://docs.discord.com/developers/discord-social-sdk/core-concepts/platform-compatibility)

## What belongs in the game client versus DiscordPHP?

### Takeaway

Use the native Social SDK inside Godot for player-authorized identity, social data, activity invites, chat, and live voice. Use DiscordPHP on the backend for its Social SDK HTTP/API and webhook capabilities—such as server-managed lobby operations, webhook intake, moderation metadata, and account-link/deauthorization bookkeeping. The two parts complement each other; DiscordPHP does not replace the native client SDK for user voice or the client's interactive friends/presence UI.

### Cited Findings

- Discord distributes the standalone Social SDK as C++ (C++20+ on current supported platforms); Unity and Unreal have generated plugins, but Godot is not listed as a first-party engine integration. The C++ SDK requires linking Discord's shared library and pumping SDK callbacks from the application's main loop. [Platform compatibility](https://docs.discord.com/developers/discord-social-sdk/core-concepts/platform-compatibility), [Standalone C++ getting started](https://discord.com/developers/docs/social-sdk/getting_started.html), [SDK installation](https://discord.com/developers/docs/social-sdk/installation.html)
- Godot's GDExtension system loads native shared libraries at runtime and supports C++ extensions through `godot-cpp`; its export descriptor can bundle native dependencies. [Godot GDExtension overview](https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/what_is_gdextension.html), [Godot C++ bindings](https://docs.godotengine.org/en/stable/tutorials/scripting/cpp/about_godot_cpp.html)
- Current DiscordPHP docs expose `$discord->lobbies` as a `LobbyRepository`, and describe DiscordPHP as wrapping Discord REST, WebSocket, and voice APIs. Its Webhook Event receiver handles Discord-signed events including lobby messages, Social SDK game DMs, and application authorizations/deauthorizations. [DiscordPHP class reference](https://discord-php.github.io/DiscordPHP/classes/Discord-Discord.html), [DiscordPHP current guide](https://discord-php.github.io/DiscordPHP/)
- Discord's Lobby API supports backend-created, updated and deleted lobbies, member add/remove/update, metadata, channel linking and messages. DiscordPHP's current public docs include the lobby repository and lobby message/moderation event types, so it is a sensible PHP integration point for server-side Social SDK operations. [Discord Lobby API](https://docs.discord.com/developers/resources/lobby), [DiscordPHP Social SDK webhook guide](https://discord-php.github.io/DiscordPHP/)
- Discord webhook events require a prompt acknowledgement (204 within three seconds); failed acknowledgements are retried for up to ten minutes. Discord's current moderation guide says backend moderation metadata updates lobby/DM messages in active game sessions, and audio moderation remains a client responsibility. [Webhook Events](https://docs.discord.com/developers/events/webhook-events), [Social SDK moderation guide](https://docs.discord.com/developers/discord-social-sdk/how-to/integrate-moderation)
- The DiscordPHP docs explicitly note that application deauthorization is the out-of-game signal that a Social SDK user's linked token/account state changed; the integration should forget that session. [DiscordPHP Social SDK webhook guide](https://discord-php.github.io/DiscordPHP/)

### Inferences

- Recommended client seam: implement a small C++ `DiscordSocialBridge` Godot GDExtension around `discordpp.h`/the shared Discord library. Expose stable Godot signals and methods for auth state, account link/unlink, friends, presence, invites, lobby membership, messages, calls, speaking indicators, mute/PTT and errors. Keep Social SDK handles and callbacks inside native code; marshal results onto Godot's main thread. GDScript can own UI and product flows without each AI coding task needing to handle raw SDK lifetimes.
- Keep DiscordPHP as an isolated long-running backend integration worker/API component, not embedded in the Godot executable. It should make authorized Social SDK server requests with server-held credentials/tokens, validate signed webhooks, map Discord identity to the game's own stable player ID, moderate text, and reconcile Discord memberships from game-server policy.
- For moderation webhooks, acknowledge promptly and do lightweight checks synchronously if practical; move slower analysis to a queue, then apply a moderation decision through the documented metadata endpoint. Do not block Discord's three-second webhook response window on an LLM or a slow external moderation service.
- DiscordPHP's regular guild voice support is bot voice in a Discord server; it is a different path from a player's Social SDK lobby voice call. Do not build a voice relay bot as a substitute for the native client SDK. The Social SDK client call is the in-game player voice path.
- A Godot C++ GDExtension is a technically appropriate bridge, but is an integration choice inferred from Discord's standalone C++ package plus Godot's native-library extension API. There is no first-party Godot Social SDK plugin documented; budget native build/package work and per-platform smoke testing.

### Gaps

- The public DiscordPHP class reference confirms the lobby repository and webhook support, but this research did not inspect the package's source signatures or enumerate every supported lobby endpoint. Confirm the exact current methods against the branch/version used by the game before implementation.
- Confirm app configuration, client type, and token flows with Discord before shipping. Discord documents some server-side alternatives for confidential clients; do not ship a client secret in the Godot build. [OAuth2 scopes and client types](https://docs.discord.com/developers/discord-social-sdk/core-concepts/oauth2-scopes)

## Where should programs, identity, outages, and authority live?

### Takeaway

Discord should be the social/communication transport, not the colony's storage engine, program runtime, or source of game truth. The Social SDK documentation provides no general-purpose user file store or remote code-execution service. Store and version in-game programs with the game's own backend; execute only a constrained game scripting language in the authoritative simulation. Discord can provide collaboration and notification surfaces around those programs, while all execution requests flow through the game server's permissions, validation, audit and sandbox controls.

### Cited Findings

- Discord documents Social SDK functions for identity, relationships, presence, invites, lobby/DM chat, linked channels and voice, not a general user filesystem or program execution service. [Social SDK overview](https://discord.com/developers/docs/social-sdk/index.html)
- Social SDK lobbies have finite lifetimes and capacity; client secrets expire after about 30 days, server idle windows max at seven days, and the lobby history endpoint returns only up to 200 messages from 72 hours. This is not a durable source-control or program repository contract. [Creating and managing lobbies](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-lobbies), [Discord Lobby API](https://docs.discord.com/developers/resources/lobby)
- Discord's terms say API/SDK data is subject to privacy obligations and that Discord may change, limit, suspend, or discontinue SDK availability. [Social SDK Terms](https://support-dev.discord.com/hc/en-us/articles/30225844245271-Discord-Social-SDK-Terms)
- Discord's rate-limit guidance distinguishes retryable transient/network/rate-limit errors from non-retryable permission/validation errors and tells callers to respect `RetryAfter`. [Handling Social SDK rate limits](https://docs.discord.com/developers/discord-social-sdk/how-to/handle-rate-limits)
- DiscordPHP's current docs show that lobby/chat messages can be intercepted on the backend and moderation metadata can be set; Discord's webhook documentation also identifies these message events as separate webhook events, not ordinary Gateway events. [DiscordPHP webhook guide](https://discord-php.github.io/DiscordPHP/), [Discord webhook event types](https://docs.discord.com/developers/events/webhook-events)

### Inferences

- Make the game's account UUID, world/colony records, permissions, inventories, player-authored programs, versions, and execution logs canonical. Persist Discord's user ID only as an optional linked external identity. Never make game authentication or the ability to operate machinery conditional on Discord linking; use the game's own account system for everyone and the provisional-account path for unlinked players.
- Store source in the game database/repository, with immutable version IDs and review/rollback. If a user wants to collaborate through Discord, post a link/version notice or use an authorized bot command to request a game-server action. Treat Discord chat, attachments and LLM text as untrusted input; do not execute PHP/GDScript/C++ or shell code from messages.
- Define a small deterministic in-game language (for example, typed sensor reads and whitelisted device commands) and run it in a server-side VM with per-tick instruction, memory, and capability limits. The LLM should produce a draft program or typed action proposal; show diffs and require the relevant in-game authorization/confirmation before publishing or applying high-impact changes. The simulator validates every action and remains authoritative.
- Make Discord availability optional to simulation correctness. If Discord is down, rate-limited, authorization expires, or access is revoked: keep the world server running, reject/queue only the affected social action, surface a retry/status, and preserve a game-native mission/status log for safety-critical simulation notifications. Use bounded exponential retry based on Discord `RetryAfter`; never repeat a non-idempotent action blindly.
- For identity/privacy, store only the minimum external identifiers and encrypted refresh/session credentials needed; never log bearer tokens. On deauthorization/unlink, clear the Discord link and cached Discord friend/profile data, revoke/delete credentials per the selected auth flow, retain the independent game account and world state, and let the player continue via provisional/game identity.
- Give players explicit controls for Discord link/unlink, presence visibility, chat source, blocking/reporting, and voice mute/deafen. Show when an in-game message is also sent to Discord. Treat linked-channel selection as a privacy-sensitive action: default to broadly visible channels or show a clear warning that every game lobby member can see messages from a private linked channel.
- Keep a Discord integration adapter with a narrow interface (`presence`, `invite`, `lobby`, `message`, `voice status`) so a platform change or SDK outage does not require changing world simulation code. For voice, allow social voice to fail independently of radio/device simulation state; the game's authority decides who is on a radio channel even if a client has no Discord call.

### Gaps

- Discord's public docs do not promise uninterrupted SDK availability, stable quotas, or an SLA; the architecture should treat each as external and subject to change.
- The exact acceptable level of cached Discord user data and final retention policy depends on implementation, jurisdiction and Discord's current terms/privacy requirements; confirm the shipping policy and have it reviewed before retaining social data.
- No reviewed Discord Social SDK documentation describes storing or running user programs. A Discord bot could still be used for narrow, permissioned commands that call the game's own API, but that is an application design choice and must never be an execution path for arbitrary program text.
